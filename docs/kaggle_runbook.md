# Kaggle runbook (K0-K5)

Every heavy step of HookSeq runs on Kaggle's free tier: 20 GB `/kaggle/working`, 14 GB RAM,
2x T4, 9 h per session. The six notebooks in `notebooks/kaggle/` are **import-and-run**:

1. import the `.ipynb`
2. attach its inputs
3. check the accelerator and Internet toggles
4. click **Save Version -> Save & Run All (Commit)**

The notebook then runs headless (you can close the browser). No cell needs editing. Inputs are
found automatically by marker files under `/kaggle/input`, and a failing step fails the
version, with the error at the end of the log.

The notebooks are generated by `scripts/make_notebooks.py`, so never hand-edit them. By default
they clone the public repo `https://github.com/Arubad/Reccomendation_system.git` at tag
**`v0.3.1`** (no token needed): the pinned release that every reported run uses. All notebooks
follow it, including the K4P profiler (part of v0.3.1). The maintainer creates and pushes the
tag; until it exists, `git clone -b v0.3.1` fails fast in the install cell. For a later
release, regenerate with the new tag:

```
.venv/bin/python scripts/make_notebooks.py --git-ref v0.3-r2
```

To point them at another repo, tag or branch (for example `hookseq-impl` for a quick
development run that will not be reported), pass `--repo-url` and/or `--git-ref`.

`GIT_REF` must be a branch or a tag (`git clone -b`), not a bare commit SHA. Every results JSON
records the commit SHA it ran at.

## 1. One-time setup

1. **Phone verification.** Go to Kaggle -> your profile -> Settings -> Phone verification.
   Without it, notebooks get neither Internet nor GPUs.
2. **Internet ON.** Every notebook clones the repo and pip-installs it, and K0 downloads from
   Hugging Face. In the notebook editor's right sidebar (Settings / Session options), set
   **Internet = On**. The notebooks declare it in their metadata, but Kaggle may ignore that on
   import, so check it once per notebook.
3. **GitHub token (only for a private fork; the default repo is public, so skip this).**
   - Create a fine-grained GitHub token with read-only *Contents* access to the repo.
   - In each notebook, open Add-ons -> Secrets -> Add a new secret. Set the label to
     **`GITHUB_TOKEN`** and the value to the token.
   - Tick the box that attaches the secret to this notebook.

   The clone cell sends the token only as an HTTP header for the repo's host. The header lives
   in the clone process's environment, so the token is never in the URL, the command line,
   `.git/config` or `.git/logs`, and it is never printed. The clone never prompts for
   credentials (`GIT_TERMINAL_PROMPT=0`): a wrong or missing token fails fast. For the public
   default repo, skip this step.
4. **Look for an existing Yambda mirror first.** Search Kaggle Datasets for "yambda". If a
   public dataset has the Hugging Face layout (`flat/50m/multi_event.parquet`, plus
   `embeddings.parquet` and `artist_item_mapping.parquet` at its root), attach it to K0. K0 then
   copies or filters from the mirror and skips the files it has instead of downloading them.
   A mirror with a different layout is simply not detected, and K0 downloads from HF as usual.

## 2. Import -> attach -> Save Version (every notebook)

1. **Import.** Kaggle -> Create -> New Notebook -> File -> Import Notebook, then upload
   `notebooks/kaggle/kN_*.ipynb`. Keep one Kaggle notebook per file (K4 trains a list of configs, or
   one config per notebook; see section 5).
2. **Attach inputs.** In the right sidebar, use Input -> **+ Add Input**. There are two ways to
   attach an earlier stage's output:
   - **(a) Directly, as notebook output:** Add Input -> **Your Work** -> pick the earlier
     notebook (for example `k0_download`). Its saved `/kaggle/working` is mounted read-only under
     `/kaggle/input/<slug>/`. This is the quickest way to chain stages.
   - **(b) As a private Dataset:** open the earlier notebook's version -> **Output** tab ->
     **New Dataset** (for later runs, use the existing dataset's **New Version** from the same
     output). Then Add Input -> Datasets -> Your Datasets. A dataset survives notebook
     deletion and can be shared between notebooks. Use it for the long-lived artifacts:
     `yambda-raw-50m`, `hookseq-processed-50m`.

   Either way, the notebook finds what it needs by marker files, whatever the mount path is.
   Check that the attached input is the **latest** version. An attached notebook output is
   pinned to a version, so use the input's menu to update it, or remove it and add it again.
3. **Accelerator.** Set it in the sidebar: **None** for K0-K3 (and K5 at 50m), **GPU T4 x2**
   for K4 (and K5 at 500m). CPU sessions do not use the weekly GPU quota.
4. **Save Version -> Save & Run All (Commit) -> Save.** If the dialog offers *Advanced
   Settings -> Always save output*, choose it. Then even a failed or timed-out version keeps
   its checkpoints. You can close the tab. The log and the output files are under the
   version's viewer (Logs / Output tabs).

Inputs under `/kaggle/input` do not count against the 20 GB working disk. Each notebook ends
with a disk check that warns above 18 GB.

## 3. The stages

| # | Notebook | Accelerator | Attach | Output (`/kaggle/working/out/`) | Marker | Est. time |
|---|---|---|---|---|---|---|
| K0 | `k0_download` | None (CPU) | nothing, or a Yambda mirror | `raw/`: `flat/<size>/multi_event.parquet`, `artist_item_mapping.parquet`, `embeddings_<size>.parquet` (subset items, float16 `embed`) | `raw/_HOOKREC_RAW_<size>` | 50m 0.5-1 h, 500m 1-1.5 h |
| K1 | `k1_eda` | None (CPU) | K0 (50m) | `reports/`: figures, `eda_stats.json` | `reports/_HOOKREC_EDA` | < 1 h |
| K2 | `k2_preprocess` | None (CPU) | K0 (same size) | `processed/<size>-<hash>/` | `_DONE` | 50m < 0.5 h, 500m 2-4 h |
| K3 | `k3_baselines` | None (CPU) | K2 | `results/*.json` (MostPop, DecayPop, iALS: val grid + test refit) | `results/_HOOKREC_RESULTS_baselines` | 50m < 0.5 h, 500m 1-3 h |
| K4 | `k4_train` | **GPU T4 x2** | K2 (+ earlier outputs of this K4 notebook, to resume) | `results/<name>-{val,test}-*.json`, `ckpt/<name>/{val,test}/` | `results/_HOOKREC_RESULTS_<name>`, `ckpt/<name>/_HOOKREC_CKPT` | see section 6 |
| K5 | `k5_eval_report` | None at 50m, **GPU at 500m** (fails fast without it) | K2 + K3 + K4 output(s) | `results/*-eval-*.json`, `*-peruser.npz`, `reports/results.md` | - | < 1 h |

What each notebook does, and the defaults its parameter cell ships with:

- **K0** runs `scripts/run_download.py --size SIZE --out out/raw [--mirror <found mirror>]`.
  - It downloads only the files still missing: `multi_event`, the artist map, and the full
    `embeddings.parquet`, which it skips if a mirror has it.
  - It filters the embeddings to the items that occur in the subset (as float16), then deletes
    the full `embeddings.parquet`, which keeps the output lean. The album map is not used, so it
    is not fetched.
  - It is idempotent: finished files are kept.
- **K1** runs `scripts/run_eda.py --raw <K0> --size SIZE --out out/reports --embeddings-file
  embeddings_<size>.parquet --emb-column embed`.
  - `TEST_TIMESTAMP = None` uses the official Yambda test start.
- **K2** runs `scripts/run_preprocess.py --config configs/data_<size>.yaml --raw <K0> --out
  out/processed`.
  - `CONFIG = None` means `configs/data_{SIZE}.yaml`.
  - `OVERRIDES` becomes `--override key=value` flags.
  - The configs read K0's `embeddings_{size}.parquet` with column `embed`.
  - **Rebuild every K2 output made before pipeline version 2.** Version 2 (fix wave F1) changed
    the protocol to the paper's Listen+ setting: ground truth is Listen+ only (no likes), warm
    users have >= 1 Listen+ train event, the baselines fit on full-period aggregates, and Listen+
    sequences exist for the `sasrec` row. `PIPELINE_VERSION` is hashed into the bundle name
    (`<size>-<hash>`), so a new K2 run never reuses an old bundle, and K3-K5 refuse to load one
    ("built by pipeline version 1 ... re-run preprocessing"). Every K3/K4/K5 result made on an
    old bundle must be re-run on the new one.
  - Output size: besides the vocab, features, truth and val/test events, a bundle holds four
    packed sequence sets (all events and Listen+ only, for `train` and `val_train`, 11 bytes per
    event) and per-period aggregates (`ui_*.npz`: 8 bytes per distinct (user, item) Listen+
    pair; `item_day_*.npz`: 10 bytes per distinct (item, day) pair; `item_hour_*.npz`: 10 bytes
    per distinct (item, hour) pair of the last 30 days; `pop_*_*.npy`: 8 bytes per item). At 50M `max_len_store: null` stores full histories (EDA §7): about 47M events per
    all-event set and about 30M per Listen+ set, so roughly 1.7 GB of sequences and about 2 GB
    in all. At 500M `max_len_store: 1024` caps each set at 1024 events per user (about 1.1 GB
    per set at 100k users), so expect about 5-8 GB in all. These are format-based estimates;
    `meta.json` records the event counts and peak RSS.
- **K3** runs `scripts/run_baselines.py ... --split val`, then `--split test`. The test run
  refits each model's best val config.
- **K4** runs `scripts/run_train.py --processed <K2> --config CONFIG --split S --ckpt
  out/ckpt/<name>/S --out out/results [--resume <earlier ckpt>/S ...]` for S in `val`, then
  `test`.
  - `CONFIGS` is a list (default: the five ablations a0-a4). They train one after another in a
    single session; the run name is the file stem. `OVERRIDES` apply to every config. A plain
    string `CONFIG = "..."` (add the line) still works and means `CONFIGS = [CONFIG]`.
  - Before each split it checks the budget left (`train.max_hours` from the resolved config,
    minus the time since the session start). Under `MIN_START_MINUTES` (default 40, 0 disables)
    it does not start and prints RESUME NEEDED. A split cut by `max_hours` also prints
    RESUME NEEDED and **stops the loop**. A config that fails fails the version (after the
    summary); finished configs stay in the output and the later ones are not started.
  - The end summary lists each config's status (done / pending / failed), val and test ndcg@10
    and GPU hours as a table, then the disk check, plus a `<name>: val, test done` line per
    finished config.
  - It skips any split whose record already exists, so a re-run is a no-op.
  - When it carries a finished split's record over from an earlier output, it also copies that
    split's `model_final.pt` and `best.pt`. So the newest K4 output alone is always enough for
    K5.
- **K5** runs `scripts/run_eval.py --processed <K2> --run <record> [--ckpt <K4>/ckpt/<name>/test]
  --out out/results` for the latest test run of every attached results input that has no
  newer eval yet. It then writes `reports/results.md` (`write_readme_tables`) and prints it.
  - Neural runs need a K4 output holding their `ckpt/<name>/test/model_final.pt`. The newest
    K4 version of that config is enough, because K4 carries finished weights forward.
  - If one run fails, the rest are still evaluated and the report is still written; then the
    version fails, listing the failed runs.

**Order:** run all of 50M first (K0 -> K1 -> K2 -> K3 -> K4 a0, then the rest -> K5) before
500M. The 50M numbers calibrate the 500M time estimates.

## 4. Resuming K4 (sessions longer than one run)

`train.max_hours: 8.0` (in `configs/sasrec.yaml`) is measured from the notebook's first cell
(`HOOKREC_SESSION_START`), for the whole session, not per config. That leaves about 1 h of the
9 h session for the final checkpoint and saving the output. When the budget runs out:

- `run_train` writes a checkpoint and exits 0 **without** a results record (or, if less than
  `MIN_START_MINUTES` of the budget is left, the notebook does not start the split at all).
- The notebook prints a **`RESUME NEEDED`** banner naming the configs and splits still pending,
  does not start any later config, and ends cleanly.
- The version shows as **successful**. That is intended, because a successful version saves
  its output.

To continue:

1. Open the same K4 notebook -> Add Input -> Your Work -> **this K4 notebook**. That attaches
   the output of the version that printed RESUME NEEDED; check that it is that version.
   Alternatively, make a Dataset from that output and attach it.
2. Keep the K2 input attached, then **Save Version -> Save & Run All** again.
3. The notebook finds each config's earlier `ckpt/<name>/_HOOKREC_CKPT` and passes `--resume
   <earlier>/ckpt/<name>/<split>`. It also copies the earlier `results/*.json` first, so
   finished splits (and whole finished configs, with their `model_final.pt`) are skipped.
   The config that was in progress continues from its last good checkpoint, with the same RNG
   and data-loader position; configs not started yet start fresh.
   Step checkpoints are not carried forward, so when a run ended in RESUME NEEDED with a config
   in progress, keep attaching the older output(s) that hold its `ckpt/<name>/` as well as the
   newest one.
4. Repeat until the log shows `<name>: val, test done` for every config. For the next round, attach only
   the newest version: each version carries the results, `best.pt` and the finished splits'
   `model_final.pt` forward.

`RESUME_INPUTS = False` in the parameter cell ignores attached earlier outputs and starts
fresh.

**After a config or code change that alters `training_hash`, rerun K4 in a fresh notebook or
set `RESUME_INPUTS=False`.** `training_hash` covers every hashed config key (for example
`train.patience`, `loss.*`, `model.*`). An old checkpoint is refused with a config-hash error,
and an old results record no longer counts as done (K4 matches records on the hash), so
attaching the earlier output only gets in the way.

**Disk, several configs:** five configs at 50M leave about 3 x 0.23 GB of final/best
checkpoints each (about 3.5 GB; step checkpoints are pruned once a split's record is written).
At 500M each config leaves about 3 x 2.3 GB, so **run at most 2 configs per notebook** there. K4
prints the projected disk use (3 kept checkpoints per config); above 18 GB it warns at 50M and
**refuses to start at 500M**: split `CONFIGS` across notebooks. The budget check
(`MIN_START_MINUTES`) only applies once something has trained in the session; if
`train.max_hours` is itself not above `MIN_START_MINUTES` the notebook fails with a clear error
instead of silently training nothing.

**Disk, one split:** at 500M a step checkpoint (model + optimizer) is about 2.3 GB. A split in progress
keeps 2 step checkpoints, plus `best.pt` and `model_final.pt`, which is about 9 GB of the 20 GB
working disk. Once a split's record is written, K4 deletes that split's step checkpoints
(`ckpt-*`), because only `best.pt` and `model_final.pt` are needed afterwards. So a version that
runs both val and test stays well under the limit. The disk check at the end warns above 18 GB.

## 5. Ablations: one notebook, all configs

The default `CONFIGS` of `k4_train.ipynb` is the ablation ladder a0-a4. Import it once, attach
K2, and Save Version: all five train in one session (about 5 x 0.5-1 h at 50M). If the budget
runs out part-way, the RESUME NEEDED banner lists what is pending; attach that version's output
and save again (section 4). To train other configs, change the list in the first cell, for
example `["configs/hookseq.yaml"]` or `["configs/ablations/a5_like_head.yaml", ...]`.
Results, markers and checkpoints are keyed by the run name (the config's file stem), so K5 can
take one K4 output for all of them.

At 500M keep the list to at most 2 configs per notebook (disk, section 4).

**Alternative: one notebook per config.** Import `k4_train.ipynb` again, name it after the
config (for example `k4_hookseq`) and set `CONFIGS` to that one file. Each config then has its
own version history and resume chain.

## 6. GPU budget (spec section 9a)

Planned at about 20 h of the roughly 30 h weekly quota. Log the actual hours after each run:
use `extra.gpu_hours` in the run JSON, or the version's run time.

| Runs | Size | Est. GPU-h | Logged actual hours |
|---|---|---|---|
| SASRec reproduction + 1-2 debug runs | 50M | ~2 | |
| Ablation ladder (about 5 configs x ~0.5 h) | 50M | ~3 | |
| Small hyperparameter sweep on the best config (about 4 runs) | 50M | ~2 | |
| SASRec baseline | 500M | ~4-5 | |
| Full HookSeq | 500M | ~5-6 | |
| Scoring / eval | both | ~1-2 | |
| **Total** | | **~17-20** | |

Recalibrate after the first 50M run: `steps_per_sec` and `wall_time_s` are in every training
record. If a 500M run exceeds a session, it chains through the resume procedure above.

## 7. Notes

- **First K4 run = fp16 check.** K4 trains with fp16 AMP on CUDA; the T4 has no bf16 or TF32.
  The GradScaler already skips steps with inf/NaN gradients. Watch the `loss` in the first
  log lines.
  - If the loss goes NaN, set `OVERRIDES = ["train.amp=false"]`; K4 passes it as `--override
    train.amp=false`. Then save a new version. It stays on the GPU in fp32, without autocast or
    the GradScaler: slower, but numerically safe.
  - `train.amp` is an operational key, like `device`, so the new version can resume the last
    good checkpoint of the fp16 run.
  - If fp32 also diverges, the problem is not precision. Lower the learning rate as well:
    `OVERRIDES = ["train.amp=false", "train.lr=3e-4"]`.
- **Single GPU.** The trainer uses one T4 by default. The second T4 stays idle.
- **Reproducibility.** Each record stores the config, the git SHA, the dataset size and the wall
  time. **The reported runs (every number in `reports/results.md`) must use a tag**, not a
  moving branch: the notebooks ship pinned to `v0.3.1` (the maintainer creates the tag).

## 8. Troubleshooting

| Symptom | Cause / fix |
|---|---|
| `no attached input contains '_HOOKREC_RAW_50m' under /kaggle/input ...` (or `_DONE`, `_HOOKREC_RESULTS_*`) | The previous stage's output is not attached, is an older version that has no marker, or is for another `SIZE`. The error lists what *is* under `/kaggle/input`. Attach the right output (section 2) and save again. |
| `no finished processed bundle '50m-*/_DONE'` | Attach the K2 output. A K2 version that failed has no `_DONE`; re-run K2. |
| `... was built by pipeline version 1, this code is version 2: re-run preprocessing (K2)` | The attached K2 output predates fix wave F1 (section 3, K2). Re-run K2 with the current code, then re-run K3-K5 on the new bundle. |
| `N processed bundles for 50m` | Two K2 outputs, with different configs, are attached. Attach only the one you want. |
| `N attached inputs contain '_HOOKREC_RAW_50m'` | Two K0 outputs (for example a notebook output and a Dataset made from it) are attached. The error lists both; remove one. |
| pip warns `cudf-polars ... requires polars<1.40, but you have polars 2.x which is incompatible` (GPU images, K4/K4P/K5) | Harmless. The GPU image ships RAPIDS `cudf-polars`, which pins an older polars, and hookrec installs the polars it needs. Nothing in hookrec imports `cudf-polars`. Ignore the warning; the run continues. |
| `polars X is installed but hookrec needs polars>=2.1` | pip did not upgrade the image's polars. The pip log above it says why, usually a conflicting pin. Save again; if it persists, report the pip log. |
| `... timed out after 600 s` (clone) or `1800 s` (pip) | Network trouble on Kaggle's side, or Internet is Off. Check the toggle and save again. |
| Disk warning above 18 GB, or the output fails to save | Usually stale K4 checkpoints. Don't keep several in-progress splits in one version. Lower `train.ckpt_every_steps` only if needed. K0 already drops the full embeddings file. |
| The version **succeeded** but the log ends with `RESUME NEEDED` | Expected: training hit `max_hours`. Follow section 4. |
| `no GPU: set Accelerator = GPU T4 x2` (K4) | The sidebar accelerator is None. Set GPU T4 x2 and save again. |
| `git clone ... failed` | Check `REPO_URL` / `GIT_REF` and that Internet is On. With the default `GIT_REF = "v0.3.1"`, the tag must already be pushed. A private fork needs the `GITHUB_TOKEN` secret, attached to *this* notebook (section 1). The clone never prompts, so a missing or invalid token fails immediately, and the token is masked as `***` in the error. |
| K5: `<run>: no ckpt/<name>/test/model_final.pt` | Attach the newest K4 output of that config, or the version that trained its test split. Outputs saved before K4 carried weights forward may lack the file. |
| K5: `rebuilt model does not reproduce the recorded ndcg@10` | Wrong checkpoint or processed dir for that record. Attach the matching K2 and K4 outputs. As a last resort, `NO_DRIFT_CHECK = True`. |
| K0: download fails or times out | Save a new version: each Kaggle session starts with an empty `/kaggle/working`, so it downloads again. Or attach a Yambda mirror (section 1). |
